## Executive Summary

### What is TAMS360?

TAMS360 (Traffic Asset Management System 360) is a comprehensive, enterprise-grade web and mobile application designed for managing road infrastructure assets including signage, guardrails, traffic signals, safety barriers, gantries, and road markings.

### Key Value Propositions

- **Complete Asset Lifecycle Management**: From capture to disposal
- **Mobile-First Field Operations**: Native PWA with offline capabilities
- **DERU Inspection Methodology**: Industry-standard condition assessments
- **Multi-Tenant Architecture**: Scalable for multiple organizations
- **Real-Time Analytics**: Dashboard KPIs and intelligent reporting
- **GIS Integration**: Full geospatial asset mapping and clustering

### Business Benefits

- **30-40% reduction** in asset inspection time through mobile capture
- **Real-time visibility** into asset condition and maintenance needs
- **Regulatory compliance** through standardized DERU inspections
- **Cost optimization** via predictive maintenance scheduling
- **Data-driven decisions** through comprehensive analytics

#### tams360_assets_v
```sql
CREATE VIEW tams360_assets_v AS
SELECT 
  a.asset_id,
  a.tenant_id,
  a.asset_ref,
  a.name,
  a.description,
  at.name as asset_type_name,
  ast.name as status_name,
  a.gps_lat,
  a.gps_lng,
  a.route,
  a.section,
  a.created_at,
  a.updated_at
FROM assets a
LEFT JOIN asset_types at ON a.asset_type_id = at.asset_type_id
LEFT JOIN asset_status ast ON a.status_id = ast.status_id;
```

#### dashboard_ci_distribution
```sql
CREATE VIEW dashboard_ci_distribution AS
SELECT
  tenant_id,
  CASE
    WHEN condition_index >= 4.5 THEN 'Excellent'
    WHEN condition_index >= 3.5 THEN 'Good'
    WHEN condition_index >= 2.5 THEN 'Fair'
    WHEN condition_index >= 1.5 THEN 'Poor'
    ELSE 'Very Poor'
  END as condition_category,
  COUNT(*) as count
FROM inspections
GROUP BY tenant_id, condition_category;
```

## Authentication & Authorization

### Authentication Flow

```
1. User Registration
   ├─ Email/Password signup
   ├─ Invitation code validation
   ├─ Create auth.users record (Supabase Auth)
   └─ Create user profile in users table

2. Login Process
   ├─ POST /auth/login with credentials
   ├─ Supabase Auth validation
   ├─ Fetch user profile from database
   ├─ Check tenant assignment
   ├─ Check approval status
   └─ Return JWT access token

3. Session Management
   ├─ Store token in localStorage (tams360_token)
   ├─ Store user data in localStorage (tams360_user)
   ├─ Token validation on each API request
   └─ Auto-logout on token expiration

4. Logout
   ├─ Clear localStorage
   ├─ Revoke Supabase session
   └─ Redirect to login
```

### Token Management

**Storage:**
```javascript
localStorage.setItem('tams360_token', accessToken);
```

**API Authentication:**

## Multi-Tenancy Architecture

### Tenant Isolation Strategy

TAMS360 implements **schema-based multi-tenancy** where all tenants share the same database tables but data is isolated via `tenant_id` foreign keys and Row Level Security (RLS) policies.

#### Tenant Resolution Flow

```
1. User Login
   └─> Fetch user profile
       └─> Extract tenant_id
           └─> Store in application state

2. Every API Request
   └─> Include Authorization header
       └─> Backend validates token
           └─> Extract user_id
               └─> Lookup tenant_id from user profile
                   └─> Filter all queries by tenant_id
```

#### Tenant Context (Frontend)

```typescript
// TenantContext.tsx
const TenantContext = createContext<TenantContextType>({
  currentTenant: null,
  setCurrentTenant: () => {},
});

// Usage in components
const { currentTenant } = useTenant();
const tenantId = currentTenant?.tenant_id;
```

#### Backend Tenant Enforcement

```typescript
// Photo upload endpoint example
const { data: userProfile } = await supabase
  .from("tams360_user_profiles_v")
  .select("tenant_id")
  .eq("id", user.id)
  .maybeSingle();

const tenantId = userProfile.tenant_id;

// All subsequent queries include tenant filter
const { data: assets } = await supabase
  .from("assets")
  .select("*")
  .eq("tenant_id", tenantId);
```

### 2. Inspection Module (DERU Methodology)

**Purpose:** Conduct standardized condition assessments using the DERU (Defects, Extent, Relevancy, Urgency) methodology to calculate Condition Index (CI) scores.

**DERU Methodology:**

```
Component CI = (D × E × R) ÷ 10

Where:
D = Defects (0-5 scale)
    0 = No defects
    5 = Severe structural failure

E = Extent (0-5 scale)
    0 = 0% affected
    5 = >80% affected

R = Relevancy (0-5 scale)
    0 = Cosmetic only
    5 = Critical safety/structural

U = Urgency (1-5 rating)
    1 = Monitor (>5 years)
    2 = Routine (3-5 years)
    3 = Essential (1-3 years)
    4 = Priority (<1 year)
    5 = Emergency (immediate)

Asset CI = Average of all Component CIs
```

**Inspection Workflow:**

```
Start Inspection
├─ Select Asset (search or scan QR)
├─ Choose Inspection Template
│   └─ Templates define components to inspect
├─ For Each Component:
│   ├─ Enter DERU Scores (D, E, R, U)
│   ├─ System auto-calculates Component CI
│   ├─ Take component photos
│   ├─ Estimate remedial cost
│   └─ Add notes/observations
├─ System calculates overall Asset CI
├─ System determines Urgency Rating (max U across components)
├─ Review Summary
└─ Submit Inspection
```

**Inspection Templates:**

Inspection templates define the components to assess for each asset type:

**Example: Guardrail Template**
```
1. Posts & Anchors (structural integrity)
2. Rail Elements (corrosion, deformation)
3. Connections & Bolts (tightness, rust)
4. End Treatments (functionality, damage)
5. Reflectorization (visibility, missing)
```

**Template Management:**
- Admin can create custom templates
- Assign templates to asset types
- Import from template library
- Version control for template changes

**Condition Index Interpretation:**
```
CI Range    | Condition     | Action Required
------------|---------------|------------------
4.5 - 5.0   | Excellent     | Routine monitoring
3.5 - 4.4   | Good          | Minor maintenance
2.5 - 3.4   | Fair          | Preventive work
```

```typescript
// Component CI calculation
export function calculateComponentCI(d: number, e: number, r: number): number {
  return (d * e * r) / 10;
}

// Asset CI calculation
export function calculateAssetCI(componentScores: ComponentScore[]): number {
  if (componentScores.length === 0) return 0;
  const sum = componentScores.reduce((acc, c) => acc + c.component_ci, 0);
  return sum / componentScores.length;
}

// Urgency determination
export function determineUrgency(componentScores: ComponentScore[]): number {
  return Math.max(...componentScores.map(c => c.u_urgency));
}
```

```typescript
// src/app/utils/offlineSync.ts

interface QueuedAction {
  id: string;
  type: 'CREATE' | 'UPDATE' | 'DELETE';
  entity: 'asset' | 'inspection' | 'maintenance';
  data: any;
  timestamp: number;
}

// Queue action for later sync
export async function queueAction(action: QueuedAction) {
  const queue = await localforage.getItem<QueuedAction[]>('sync_queue') || [];
  queue.push(action);
  await localforage.setItem('sync_queue', queue);
}

// Sync queued actions when online
export async function syncQueue() {
  const queue = await localforage.getItem<QueuedAction[]>('sync_queue') || [];
  
  for (const action of queue) {
    try {
      await processAction(action);
      // Remove from queue on success
      await removeFromQueue(action.id);
    } catch (error) {
      console.error('Sync failed:', action, error);
      // Keep in queue for retry
    }
  }
}

// Process queued action
async function processAction(action: QueuedAction) {
  const endpoint = getEndpointForAction(action);
  const method = getMethodForAction(action);
  
  await fetch(endpoint, {
    method,
    headers: {
      'Authorization': `Bearer ${getToken()}`,
      'Content-Type': 'application/json'
    },
    body: JSON.stringify(action.data)
  });
}
```

- `ASSET_LOOKUP_MISSING` - Missing lookup tables (seed data)
- `TENANT_NOT_FOUND` - User not assigned to tenant
- `ASSET_CREATE_FAILED` - Asset creation error

### Rate Limiting

Currently no rate limiting enforced. Future implementation planned:
- 100 requests/minute per user
- 1000 requests/hour per tenant
- Burst allowance: 20 requests

### Role-Based Routing

**Route Guards:**
```typescript
// RoleGuard.tsx
interface RoleGuardProps {
  allowedRoles: string[];
  children: React.ReactNode;
}

const RoleGuard: React.FC<RoleGuardProps> = ({ allowedRoles, children }) => {
  const { user } = useAuth();
  
  if (!user) {
    return <Navigate to="/login" />;
  }

      <div className="p-8 text-center">

      </div>
    );
  }
  
  return <>{children}</>;
};

  <RoleGuard allowedRoles={['admin']}>

  </RoleGuard>
} />
```

## Data Flow & Workflows

### Asset Lifecycle

```
Asset Creation
    ├─ Manual Entry (Desktop)
    │   ├─ Form input with validation

    │   ├─ Photos uploaded

    │
    └─ Bulk Import
        ├─ CSV file upload
        ├─ Column mapping
        ├─ Validation
        └─ Batch insert

Asset in Service
    ├─ Regular Inspections
    │   ├─ DERU scoring
    │   ├─ Component photos
    │   └─ CI calculation
    │
    ├─ Condition-Based Maintenance
    │   ├─ Triggered by CI threshold
    │   ├─ Scheduled work
    │   └─ Completion tracking
    │
    └─ Routine Monitoring
        ├─ Dashboard KPIs
        ├─ Trend analysis
        └─ Alert generation

Asset End-of-Life
    ├─ Status → "Pending Removal"
    ├─ Final inspection
    ├─ Removal work order
    ├─ Completion documentation
    ├─ Status → "Removed"
    └─ Historical data retained
```

### Inspection Workflow (Detailed)

```
1. Pre-Inspection
   ├─ Select asset (search/scan/map)
   ├─ Verify asset details
   ├─ Choose inspection template
   └─ Review previous inspections

2. Component Assessment
   ├─ For each component:
   │   ├─ Assess Defects (D: 0-5)
   │   ├─ Measure Extent (E: 0-5)
   │   ├─ Rate Relevancy (R: 0-5)
   │   ├─ Determine Urgency (U: 1-5)
   │   ├─ System calculates CI = (D×E×R)/10
   │   ├─ Take component photo
   │   ├─ Estimate remedial cost
   │   └─ Add notes/observations

3. Inspection Summary
   ├─ System calculates overall CI (average)
   ├─ System determines urgency (max U)
   ├─ Review all components
   ├─ Add general notes
   └─ Reviewer validates

4. Submission
   ├─ Save to database
   ├─ Update asset's latest CI
   ├─ Trigger maintenance if CI < threshold
   ├─ Generate notification if urgent
   └─ Sync photos to storage

5. Post-Inspection
   ├─ Generate inspection report (PDF)
   ├─ Email to stakeholders (optional)
   ├─ Update dashboard metrics
   └─ Add to asset history
```

### Photo Upload Flow (New v2.1.0)

```
1. User Uploads Photos (Bulk)
   ├─ Select zip file or folder
   ├─ Files named: {assetRef}_{photoNumber}.ext
   └─ Initiate upload

2. Preflight Validation
   ├─ Parse filenames
   ├─ Check asset exists
   ├─ Validate file types
   ├─ Check file sizes
   └─ Generate preview

3. Backend Processing (per photo)
   ├─ POST /photos/get-upload-url
   │   ├─ Extract assetRef from filename
   │   ├─ Lookup user's tenant_id
   │   ├─ Check if asset exists
   │   │   ├─ YES → Use existing asset_id
   │   │   └─ NO → Auto-create asset
   │   │       ├─ Infer type from prefix
   │   │       ├─ Lookup asset_type_id
   │   │       ├─ Lookup status_id (Active)
   │   │       ├─ Create with required fields
   │   │       └─ Handle duplicates (race)
   │   └─ Return signed upload URL
   │
   ├─ Client uploads to storage
   │   ├─ PUT to signed URL
   │   ├─ Direct to Supabase Storage
   │   └─ Progress tracking
   │
   └─ POST /photos/save-metadata
       ├─ Save photo record
       ├─ Generate signed view URL
       └─ Return photo_id

4. Completion
   ├─ Show upload summary
   ├─ Display errors (if any)
   ├─ Link to view assets
   └─ Update asset photo counts
```

### Offline Sync Flow

```
1. User Goes Offline
   ├─ OfflineContext detects network loss
   ├─ Display offline banner
   └─ Enable offline mode

2. Offline Actions
   ├─ User creates/edits data
   ├─ Data saved to localForage (IndexedDB)
   ├─ Action queued in sync_queue
   └─ UI shows "pending sync" badge

3. User Comes Online
   ├─ OfflineContext detects network
   ├─ Trigger syncQueue()
   ├─ Process queue in order
   │   ├─ POST queued creations
   │   ├─ PUT queued updates
   │   ├─ DELETE queued deletions
   │   └─ Handle conflicts (last-write-wins)
   ├─ Remove successful actions from queue
   └─ Display sync complete notification

4. Conflict Resolution
   ├─ Server-side timestamp comparison
   ├─ Last write wins strategy
   └─ User notified of conflicts
```

## Troubleshooting & Maintenance

### Common Issues

#### 1. User Cannot Login

**Symptoms:** "User profile not found" error

**Diagnosis:**
```sql
-- Check if user exists in auth.users
SELECT * FROM auth.users WHERE email = 'user@example.com';

-- Check if user profile exists
SELECT * FROM users WHERE email = 'user@example.com';
```

**Solutions:**
- User not approved: Admin must approve in User Management
- Profile missing: Run diagnostic endpoint `/diagnostics`
- Token expired: User must log in again
- Tenant not assigned: Assign user to tenant

#### 2. Photos Not Uploading

**Symptoms:** "Failed to create asset" or "User not found"

**Diagnosis:**
```typescript
// Check backend logs for specific error
console.log('Photo upload error:', error);

// Common causes:
// 1. Asset lookup tables missing (asset_types, asset_status)
// 2. Tenant not found for user
// 3. File too large (>10MB)
// 4. Invalid file type
```

**Solutions:**
- Run Seed Data to create lookup tables
- Verify user has tenant_id assigned
- Check file size/type constraints
- Check storage bucket permissions

#### 3. Map Not Loading

**Symptoms:** Blank map or "Failed to load tiles"

**Solutions:**
- Check internet connection
- Verify OpenStreetMap tiles accessible
- Clear browser cache
- Check for JavaScript errors in console
- Verify GPS coordinates are valid

#### 4. Offline Sync Failing

**Symptoms:** "Sync failed" notification

**Diagnosis:**
```typescript
// Check sync queue
const queue = await localforage.getItem('sync_queue');
console.log('Pending sync items:', queue);
```

**Solutions:**
- Check internet connection
- Verify API token still valid
- Clear sync queue and re-enter data
- Check for data validation errors

#### 5. Dashboard Data Incorrect

**Symptoms:** Wrong KPI numbers or missing charts

**Solutions:**
- Check database views exist (`dashboard_*`)
- Verify RLS policies allow data access
- Refresh dashboard (manual button)
- Check browser console for API errors
